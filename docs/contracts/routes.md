# Contract: server routes

One detached Node process per state dir (default `~/.onionskin/`, override `ONIONSKIN_STATE_DIR`). The product name and bin name live in `src/constants.js`.

## Transports

- **CLI to server: Unix domain socket** `<state>/s.sock` (mode 0600, state dir 0700 and ownership-checked on every start). Routes below under `/cli/*` and `/health`. Not served on TCP.
- **Browser to server: TCP 127.0.0.1, random port.** Routes under `/` and `/api/*`. Not served on the socket.
- Browser routes (all need the cookie AND the launch token, header `x-onionskin-token`; the event stream takes it as `&t=`): `GET /api/bootstrap` (no token in the answer; `{session, product, settings, suggest}`, where `suggest` is `{on, name, tasks, unavailable}`: whether quick fixes are set up on this Mac, which stamps ask the model first, and `{code, line}` when Apple's model cannot answer now (the page then shows the line instead of the offer and Fix grammar goes to the agent), else null; `tasks` is `["grammar"]`, or all three with the test stand-in back end), `GET /api/events`, `GET /api/file`, `GET /api/stale?sha=` (`{stale, diskSha}`: has the disk changed since the page loaded `sha`; never while a batch is delivered), `GET /api/history` and `GET /api/history/:id` (change history, below), `GET /api/style`, `POST /api/style` (writing preferences, below), `GET /api/voice`, `POST /api/voice/{answer,guide,forget,learning,draft/discard}` (learning and the voice guide, below), `POST /api/voice/build?s=` (Build my voice guide, below), `GET /api/settings`, `POST /api/settings`, `GET /api/background`, `POST /api/background`, `POST /api/background/remove` (per-machine background, below), `GET /api/stamps`, `POST /api/stamps` (own stamps, below), `GET /api/setup-checker`, `POST /api/setup-checker` (deeper-check setup, below), `GET /api/setup-rewriter`, `POST /api/setup-rewriter` (quick-suggestion setup, below), `POST /api/suggest`, `POST /api/suggest/use`, `POST /api/suggest/warm` (quick fixes, below), `POST /api/{claim,draft,send,takeback,revert,resolve,close,show-copy,dismiss-conflict,export-tracked}`.`POST /api/{claim,draft,send,takeback,revert,resolve,close,show-copy,dismiss-conflict,export-tracked}`. `show-copy {path}` runs `/usr/bin/open -R` only for a path this server wrote (a conflict copy or a tracked-changes copy). A request without a token gets `403 token_required` (bootstrap: `401`) and a hint to run `onionskin open` again. The launch token is delivered once, as `<meta name="onionskin-launch">` in the response to the launch link; a reload re-presents it from sessionStorage.
- Every response (any route, any status) carries `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data:; font-src 'self' data:; connect-src 'self' blob:; worker-src 'self' blob:; frame-src 'self' blob:; base-uri 'none'; form-action 'none'`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`.

| route | |
|---|---|
| `GET /health` | `{ok, pid, protocol}` |

Otherwise unchanged: validates (realpath, regular file, owned by us, `.docx/.xlsx/.pptx`, valid package of that format, macro types refused), creates or reuses the session, stores the first-ever original, mints a launch nonce. `{key, url, state, name}` |
| `GET /cli/poll?file=&ack=1&full=1&holder=` | long poll. Resolves with the batch plus `lease: {holder, token}` (state becomes `working`, lease starts; the token is minted per delivery, so a batch that goes back to pending and is delivered again gets a new one) or `{status:'superseded'}` (a newer poller took over) or `{status:'closed'}`. `ack=1` renews the lease of a run in progress. The FIRST batch a holder receives in a session is the complete one; later batches are compact only when the poll passes `compact=1` (only `reply --then-poll` does) and the holder was briefed already (memory of the running server only); a plain poll is never compact. A compact batch has: same `instructions` and `untrusted_document_evidence`, the first two `agent_rules`, `lease`, `lease_ticket`, `compact: true` and a `next_step` that is the `reply` command, no `how_to_apply`. `full=1` always returns the complete form (see `batch.schema.json`). The stored batch that `GET /cli/batch` returns is always the complete one. Opens the session if it is not known yet. Client disconnect deregisters the poller. |
| `GET /cli/status?file=` | `{state, locked, pollers, pending_batch, delivered_batch, lease_expires_at, comments, unsent_edits, activity}` |
| `GET /cli/batch?file=` | `{state, batch}`: the batch delivered to the agent (anchors for `apply`), `batch: null` when none is in progress. |
| `POST /cli/agent-write {file, base_sha256, bytes_b64, holder, batch_id, lease_token, ops?, partial?}` | `apply` through a live session. `ops` (the ops `apply` ran to make the bytes) and `partial` are kept in memory as the record of this write; a later XLSX merge runs them again on the version before the write and uses them only when the result matches the bytes cell for cell. Missing or invalid `ops` only means a later merge hands the user's edits back; the write itself is unaffected. Accepted only while a batch is delivered (state `working` or `queued`, both hold a live lease) and only for the lease holder (`poll` picks a holder: `ONIONSKIN_HOLDER`, else the id the file's last poll used, else a random one; `<state>/holders/<key>.json` keeps only that holder id, never the token). `holder`, `batch_id` and `lease_token` are ALWAYS required (400 `missing_lease`, no matter what else is sent); a `batch_id` or `lease_token` that is not the current delivery's is 409 `stale_batch`. 409 `not_working` (state in the body), 403 `not_lease_holder`, 409 `conflict` (disk hash is not `base_sha256`; nothing written), 422 `invalid_package`. Otherwise: snapshot of the bytes on disk, atomic write, the pre-agent version stays the newest snapshot, lease renewed. `{ok, sha256, lease_expires_at}` |
| `POST /cli/commit {file, bytes_b64, base_sha256?, holder, batch_id, lease_token}` | candidate bytes made from a COPY by another tool: the same authenticated write as `agent-write` (lease required, 400 `missing_lease`; 409 `not_working`, `stale_batch`, `conflict`; 422 `invalid_package`) with snapshot label `before agent commit`. Without `base_sha256` the base is the hash this server last wrote or delivered for the batch. `{ok, sha256, lease_expires_at}` |
| conflicts | A write whose base is not the disk hash, or a disk that changes just before the rename, is refused with 409 `conflict` and the original is not touched. The held version is saved as `<name> (Onionskin copy YYYY-MM-DD HHMM)[ n].<ext>` next to the original (local time; same mode, xattrs and ACL as the original; never overwrites): for a user Send the page's bytes, for `agent-write`/`commit` the candidate. The 409 body carries `side` (`user`|`agent`), `copy_name`, `copy_path`, `copy_error`, `can_reveal`; `apply`/`commit` turn an agent-side one into `status: "outside_change"` plus `outside_change {copy_path, copy_name, instruction}` (exit 5). The agent-side case also records an activity entry (`kind: outside_change`) and `conflict` in the session view; the batch stays delivered so the agent can run `done`, which flags it (`outside_change`, warn). |
| `POST /cli/apply-report {file, holder, batch_id, lease_token, run, problems:[{key,op,status,code,reason}], applied:[key]}` | what `apply` could not do (codes and short reasons, no document text), from the lease holder; kept with the delivered batch and turned into flags at `done`. Problems are keyed by op (`<index>:<op>`): a later run replaces what an earlier run said about the same op, and an op listed in `applied` clears it. 409 `not_working`, 403 `not_lease_holder`, 409 `stale_batch`. |
| `POST /cli/done {file, results, holder, batch_id, lease_token}` | `results = {summary, document_instructions_ignored?, suggestions? (a review batch only, see `POST /api/review`), voice_draft? (a voice batch only, see below), results:[{comment_id, status:'done'|'declined', note} | {comment_id, status:'asked', ask, options}]}`. `asked` (a question for the user instead of a decline) is accepted only for a comment of the delivered batch (anything else is flagged `unknown_result` and changes nothing); the question and options are cleaned as untrusted text and checked (`src/question.js`: 1 to 160 characters, 2 to 4 different options of 1 to 40 characters, no `://` or `www.`, never cut), at most 3 per `done`, one per comment. A question that fails a check makes the comment `declined` with a fixed note and a `bad_question` warn flag (`reason`: `bad_question`, `too_many_questions` or `already_asked`); the rest of the results are kept. The comment stores `question = {text, options}` and its status becomes `asked`. `summary` is cut at 400 characters; `document_instructions_ignored` (optional) is read from its first 50 items: only strings count, each is sanitized as untrusted text (200 characters), empty ones are dropped, repeats that differ only in case count once, and the first 5 distinct are kept (`documentInstructionsIgnored`; `documentInstructionsIgnoredMore: true` when a sixth distinct one was reported). The page shows a count chip and a fixed note, never the strings. 409 `no_batch` when nothing is in progress (taken back, lease expired, already done); 409 `stale_batch` when the batch, holder or lease token is not the current delivery's (a late `done` from an agent whose lease expired cannot finish another agent's batch); 400 `missing_lease`. The CLI takes the delivery only from `--lease <batch id>:<token>` (printed in the commands of the batch `poll` hands out) and refuses to call this route without it while a batch is delivered: `results.json` carries no credentials and nothing falls back to what the last `poll` saved. Flag strings that come from the document are cut to one short line (see `cleanFlag` in `src/sanitize.js`). Runs the package checks (Node always; Python/LibreOffice when `ONIONSKIN_PYTHON` or `<state>/venv` exists, see `docs/contracts/ops.md`), the LibreOffice conversion is not waited for (it finishes later and updates the entry, see ops.md), records the activity entry (`flags` with severity `info|warn|error`, `checks`, `revertRecommended`, `changes` = the regions the agent changed, see anchors.md), emits `reload`. `{ok, flags, checks}`. `voice_draft` on any other batch is flagged `voice_draft_not_allowed` and stored nothing; while a batch is out, `voice_guide_changed_outside_onionskin` (warn) says the guide's guard put `voice-guide.json` back. A voice batch ends differently: `voice_draft` is checked by `cleanVoiceDraft` (the trust boundary) and stored as `<state>/voice-draft.json` for the person's review, never copied into the guide; a refused one is flagged `bad_voice_draft` (`reason`: the check's code, never the draft's text) and stores nothing; any other field (`voice_guide`, `on`, `save`) changes nothing, `results[]` entries are `unknown_result`. The activity entry has kind `voice` and a fixed summary (never the agent's), there is no history update and no analysis, and the event is `state`. A file that changed during a voice run is recorded as a withdrawn run (an `agent` entry with `voice_run_changed_file` and `file_changed_outside_onionskin`, Revert-able) and the event is `reload`. `{ok, flags, checks: null, voice_draft: "kept" \| "refused"}` |
| `GET /cli/batch-file?batch_id=` | `{file}`: the real path of the session whose delivered batch has that id, `file: null` when none. Lets `reply --lease <ticket>` run without a file argument; the lease token is still checked at the write. |
| `POST /cli/stop` | graceful exit. Every waiting poll is first answered with `{status: "closed", reason}`, so a poll does not treat the stop as a lost connection and start the server again. |

`onionskin reply` is a composite of these routes, not a route: it reads `GET /cli/batch`, builds ops from the replies (target and `expect` from the stored batch), runs the `apply` path (`POST /cli/agent-write`, `POST /cli/apply-report`) and, when the write succeeded, the `done` path (`POST /cli/done`), then optionally polls with `ack=1`. See `ops.md`.

The session object the page receives (`GET /api/bootstrap`, the `state` event, the `/api/send` answer) carries `stage` while a batch is delivered: `"delivered"` (an agent's poll has the batch), `"writing"` (an apply or commit for it is running or has landed), `"checking"` (`done` is running its checks); `null` when no batch is delivered. The server sets it on delivery, on the arrival of `agent-write`, `commit` and `apply-report`, and when `done` starts, and broadcasts every change like any other session change; a failed `done` puts the earlier stage back. The session object also carries `local`: true while the delivered batch is a run on this Mac, through all its stages, so the page words the wait without an agent ("Working on this Mac", no progress bar). Everything a person reads about such a run says so: its outside-change note and banner (`conflict.local`), the lease-expiry entry (`by: "local"`), the mid-run entries, the Revert entry ("Reverted to the version before this change.") and the History row of that revert ("Reverted change made on this Mac"); an agent's run keeps the agent's words. The value `"local"` means a whole Send is being done on this Mac, no agent involved (src/local.js, the page says "Doing this on your Mac"); it is shown while that delivery has not started writing, and the run then moves through `"writing"` and `"checking"` like an agent's. The activity entry of such a run keeps `kind: "agent"` (Revert, the late checks and the What changed note treat it as a run) and adds `by: "local"` and `localNote` (the Send's overall note); its history update has kind `local`. A review (`POST /api/review`) finishes with an entry of `kind: "review"` (`reviewKind`, `summary` "The agent made {n} suggestions." or "The agent had no suggestions.", `suggestions` and `suggestionsDropped` counts, `checks: null`), no history update and a `state` event, not `reload`: nothing in the file changed, so it is never the run Revert or the late checks look for. The session object also carries `suggestions`: the review's cards, newest first, `{id, reviewId, kind: "edit"|"note", label, before, after?, why?, note?, status, at}`. `label`, `before` and `at` (where the card points: DOCX `ordinal`, `para_id`, `body_path`; PPTX `slide_id`, `slide_index`, `shape_id`; XLSX `sheet`, `range`) come from code and the file; `after`, `why` and `note` are the agent's text, checked by `done`; the op Accept runs stays on the server. `status`: `open`, `accepted`, `rejected`, `dismissed`, `stale` (the text there changed, so it was not applied), `replaced` (a newer review came in while it was open). Reverting an Accept puts its cards back to `open`.

**Runs on this Mac.** Before a pending batch goes to a poller, the server asks its local runner once per batch id whether it can do the whole batch itself (only when every part of the Send qualifies; a planner in `PLANNERS` decides, from the person's own words; the quick-change planner of `src/quick-plan.js` is the first, see `POST /api/quick`). Yes: the batch is delivered to the reserved holder `onionskin-local` with a fresh token, no waiting poller is taken, and the runner answers it through the same `reply`, `apply`, agent-write and `done` code as an agent, so the lease, the expect, protected and package checks, the compare-and-swap, the snapshot and Revert are the same. The local token is never written to `<state>/tickets`, so `status --ticket` cannot hand it out, and `GET /cli/poll?holder=onionskin-local` is refused (400 `reserved_holder`). When the runner cannot finish before anything is written (no match, a planner error or timeout after 5 s, an expect or protected refusal) the batch goes back to pending unchanged and the next poll gets it with a new lease (the agent never sees that it was tried); queued comments become drafts again, as at lease expiry. A write refused because the file changed finishes the run with every comment declined and the note "The file changed while this was being done, so nothing was written. Send it again." A batch that comes back (hand-back, lease expiry, restart) is never tried locally again. After a restart, a local delivery that had not written is pending again; one that had written expires at the first tick, which records what was written. Reverting a local run marks its comments (and its note, when the note box was empty: the note comes back into it) so the next Send of them goes to the agent. A run started by Onionskin itself (`startLocal`: an accepted review card, or a quick fix's Use) never goes to an agent: when it ends without writing (`dropLocal`, a restart, a lease expiry) a quick fix's comment is a draft again and carries `localHint`, "This could not be changed on this Mac, so nothing was written. Press Send to ask the agent." (on a lease expiry after a write it is a draft again without it). `setDraft` keeps `localHint` while the comment's words stay the same. It means something only while the comment is a draft: an ordinary Send does not remove it, so the page shows it on draft comments only.

CLI exit codes: 0 success (poll prints the batch, or `{"status":"timeout"|"superseded"|"closed"}`), 1 any error (message on stderr).

## Browser routes (TCP)

Auth chain: `GET /?s=<key>&n=<nonce>` consumes the single-use nonce (60 s) and sets `onionskin_sid_<port>=<random>; HttpOnly; SameSite=Strict; Path=/` (the cookie name carries the port because cookies are shared across ports on one host). The page strips `n` with `history.replaceState`, then calls `GET /api/bootstrap` which returns the per-session API token. Without a valid nonce or cookie every route answers 403 or 401.

All requests: `Host` must be exactly `127.0.0.1:<port>`; `Origin`, if present, must be exactly `http://127.0.0.1:<port>`; `Sec-Fetch-Site`, if present, must be `same-origin`.
`/api/*` additionally needs `x-onionskin-token` (timing-safe compare), except `GET /api/bootstrap` and the SSE route (cookie only).
`POST` additionally requires `Origin` and `Sec-Fetch-Site: same-origin` to be present and `Content-Type: application/json`.

## Background agent (src/agent-runner.js)

The session object carries `agent: {state, cli, show, activity, failure}`: `state` is `none` | `starting` (spawned, or waiting for a slot or a restart) | `ready` (its poll waits) | `working` (it holds the delivered batch) | `external` (an agent with another holder polls or holds the file) | `failed` | `handover` (open in Terminal); `cli` is `"claude"` or null; `show` is the per-machine switch; `activity` is at most 50 `{at, text}` lines of fixed words (never agent or document text); `failure` is null or `{code, resetsAt?, update?, codex?}` with `code` one of `not_installed` (`update: true`: a Claude Code older than 2.1.323; `codex: true`: no Claude Code but Codex is on this Mac, so the page says to ask Codex for the file), `signed_out`, `limit`, `crashed`, `too_many_restarts`, `refused`. While it waits for one of the 3 slots the view also has `busy: true` (the page adds "Another document's agent is busy.").

Starts: `POST /cli/open` with `agent: "background"`; a Send that leaves the session `stranded` with no poller (at once when the session was opened for the background agent, else after 20 s if it is still stranded with no poller); `POST /api/agent {action: "start"}`. Never while another holder polls or holds the delivery. At most 3 run at once; a 4th is `starting` until a slot frees. Stops: Close session (its poll is answered `closed`, so it ends by itself; its group is stopped only if it is still running 10 s later), server shutdown (every group is signaled before exit), 20 minutes with no tab and no delivered batch, a poll by another holder (the background poller is told `superseded`, and a background poll while another holder waits gets `superseded` at once instead of taking over), `stop`, `terminal`. A crash (or an end of its turn while it should listen) releases a delivery it held at once (`Sessions.releaseAgent`, the same steps as a lease expiry: a run that wrote is recorded with Revert, one that did not is pending again) and restarts after 2, 4, 8, 16, 32 s with `--resume <session id>`; at most 5 starts per document per rolling hour, then `too_many_restarts`. `error_max_turns` (200 turns) starts a fresh conversation and is not counted. `signed_out`, `limit` and `refused` (denials in the result while it still held the batch) never restart by themselves.

The command (Claude Code, `cwd` = `<state>/agents/<key>` created 0700 by real path, stdin closed, its own process group): `claude -p <fixed prompt> --append-system-prompt <this build's SKILL.md> --model <agent.model, default sonnet> --session-id <uuid> --output-format stream-json --verbose --max-turns 200 --restricted --tools Bash,Read,Write --allowedTools "Bash(onionskin poll:*)" "Bash(onionskin reply:*)" "Bash(onionskin status:*)" "Read(//<skill>/reference/**)" "Read(//<work folder>/outline/**)" "Edit(//<work folder>/**)" --add-dir <skill>/reference --add-dir <work folder>/outline --permission-mode dontAsk --permission-prompts none --setting-sources "" --strict-mcp-config --disable-slash-commands`. Its environment is only `HOME, USER, LANG, TMPDIR, PATH=<state>/agents/bin:<node dir>:/usr/bin:/bin, ONIONSKIN_STATE_DIR, ONIONSKIN_HOLDER=onionskin-bg-<key>, ONIONSKIN_AGENT_DIR=<work folder>, BASH_DEFAULT_TIMEOUT_MS=600000` (plus `ONIONSKIN_TRACE` when the server has it); `<state>/agents/bin/onionskin` runs the server's own `src/cli.js`. Before each start `claude --version` (at least 2.1.323) and `claude auth status --json` (`loggedIn: true`) run with that environment, 5 s each. The prompt has the file path, the work folder and the poll timeout (590 s) filled in, never document text. Proven forms (one real probe, Claude Code 2.1.323): `Edit(//abs/**)`, `Edit(/rel/**)` and `Edit(./rel/**)` all allow Write under the folder and a folder with no rule is denied; a Read outside the working folders is refused by `--restricted` even with a `Read(//...)` rule, so `--add-dir` is what allows the reference folder; `onionskin reply ... --file <path>` passes; an assignment prefix (`ONIONSKIN_HOLDER=x onionskin status ...`) is refused.

The reply travels by file: Write to a new `<work folder>/reply-<batch_id>.json`, then `onionskin reply --lease <ticket> --then-poll --file <that file>` (older reply files are deleted at the next delivery). For a holder starting with `onionskin-bg-` or `onionskin-term-`, `reply` refuses `--json`, stdin and any `--file` whose real path is not exactly `ONIONSKIN_AGENT_DIR/reply-<the batch id of --lease>.json`, a regular file (`bad_reply`, `lease_kept: true`), and a JSON parse error names a position at most, never the input. Its `poll` (and `reply --then-poll`) never starts a server and never reconnects: no server, or a lost connection, prints `{"status":"closed","reason":"the server stopped"}` and exits 0. Both holders' polls never start a server, and their ids are never saved in `<state>/holders`. When an agent process ends, its holder's polls still registered (a poll child that outlived it) are answered `closed`, and a background poll for a file whose agent the runner started but is not running now is answered `closed` at once. Its polls do not count as busy for the idle shutdown.

The document outline: such an agent cannot open the file, so every edit batch delivered to a holder starting with `onionskin-bg-` or `onionskin-term-`, complete or compact, also carries `untrusted_document_evidence.outline` (and `outline_more` when units were left out), built at that delivery by `src/review.js` `outlineOf` from the file as it is then (the bytes its ops are checked against): the units of a review (DOCX paragraphs with text, PPTX text shapes, XLSX non-empty cells, in order, at most 300, text through `untrusted()` at 1,000 characters), each with the op `target` (DOCX `{para_id?, body_path, text_hash}`, PPTX `{slide_id, shape_id}`, XLSX `{sheet, range}`) and `expect: {text_hash}` to copy, no target on a protected unit, `text_exact: false` when the text shown is cut or cleaned. It is cut from the end so the printed batch stays within 28,000 characters (one shell output; a longer Bash output reaches Claude Code's model only as a short preview of a saved file the agent cannot read). When that is not the whole document, the server also writes the complete outline of that batch, up to 2,000 units, to `<state>/agents/<key>/outline/outline-<batch id>.jsonl` (0600, atomic; one unit per line with the same fields, every line under 1,900 characters so Claude Code's Read tool pages it with offset and limit) and the batch names it in `outline_file` with `outline_file_units`; `outline_more` then counts only the units past the file. Older outline files of the session go at each such delivery, and the folder on Close. That folder is the only part of the work folder the agent may read (`--add-dir <work folder>/outline` and `Read(/<work folder>/outline/**)`): not its transcript, the Terminal command or reply files. A review batch (it has `units`) and a voice request get none, and the stored batch (`GET /cli/batch`, the page) never carries it. A note-only Send ("change the title") is answered with top-level `ops` built from it.

The holder prefixes `onionskin-bg-` and `onionskin-term-` are reserved: `GET /cli/poll` with either prefix and another file's key is 400 `reserved_holder`. Every other holder sees the same routes, outputs and exit codes as before.

Records and files: `<state>/agents/<key>.json {pid, pgid, lstart, holder, key, cli, session_id}` (0600, written at spawn, removed at exit). A signal goes to `-pgid` only when `pgid` equals `pid` and while `ps -o lstart= -p <pid>` equals `lstart` (SIGTERM, then SIGKILL after 4 s, checked again). A server that starts reads every record, stops the groups that still match and deletes all records. `<state>/agents/<key>/transcript.jsonl` (0600) is the agent's stream; Close session deletes the work folder and runs `claude purge <work folder> --yes`, which removes Claude Code's own copy under `~/.claude/projects` (also after a server restart, when the runner never started that agent). A server stop keeps both until Close session, since the session is kept too. "Open in Terminal" writes `<work folder>/open-agent.command` (0700: `cd`, `env -i` with the same environment and the holder `onionskin-term-<key>`, then `claude --resume <id>` with the same limits, without `-p` and the stream flags) and opens it with `open -a Terminal`.

Tests: a process with `NODE_TEST_CONTEXT` (every `node --test` file, and the servers they start) never starts an agent unless `ONIONSKIN_AGENT_PATH` is set; `ONIONSKIN_AGENT_PATH` (dirs searched first) and `ONIONSKIN_AGENT_CLI` (`claude`, or `none` to turn the agent off) are the seams.

## State machine (server, per session)

`idle` (no poller) / `listening` (a poller waits) / `working` (batch delivered, lease running; `locked` is true: the server refuses document bytes from the page; the page stays editable in every format and merges afterwards with `POST /api/merge`) / `queued` (working, plus comments sent meanwhile) / `stranded` (batch pending, nobody polling, or the lease expired; document editable; the view carries `strandedCommand`, the agent's `poll` line, and `startCommand`, the `onionskin <file>` line a person runs in a terminal to start an agent) / `closed`.
Lease: `ONIONSKIN_LEASE_MS` (default 15 min), renewed by `poll --ack`; expiry returns the batch to pending (stranded) and records a `lease_expired` activity entry. `<state>/leases/<key>.json` mirrors `{holder, expiresAt, baseSha256}`.
Start and stop: the probe-unlink-listen sequence runs under `<state>/start.lock` (created exclusively, holds the pid; a lock whose pid is gone is taken over), so two servers starting at once cannot unlink each other's live socket. On shutdown a server unlinks the socket and `server.json` only if `server.json` still records its own pid.
Idle shutdown of the server: `ONIONSKIN_IDLE_MS` (default 2 h with no pollers, no delivered batch, no SSE clients).

## State files (all under the 0700 state dir, created exclusively with mode 0600, then renamed into place)

`server.json {pid, port, protocol}` (no secrets), `sessions/<key>.json` (comments, note, batches, activity), `leases/<key>.json`, `tickets/<batch id>.json` (0600: the delivery's holder and token, removed when it ends), `holders/<key>.json` (holder id only), `snapshots/<key>/<sha256>.bin` + `index.json` (content addressed; original kept forever; at most 20 other versions and 2 GB; a free-space check before every snapshot), `history/<key>/<before>_<after>.json` (0600: counts and places of one snapshot pair, a cache that can be deleted at any time; the updates themselves are `history` in `sessions/<key>.json`: id, kind, time, the two snapshot hashes, the agent's summary).

## Writing preferences (browser routes, per machine)

Like the background settings: not tied to a session, not editor-gated, same cookie, launch token and (for POST) exact Origin and JSON content type. | `POST /api/voice/learning {on}` | the "Learn from my edits" switch; off stops new records and keeps what is stored |

`POST /api/voice/build?s= {open_file, edits, comments, improve, texts, files}` ("Build my voice guide", `buildVoiceRequest` in `src/voice-learn.js`): session-scoped and editing tab only (409 `not_editor`), not on the CLI socket, with its own body cap (five 20 MB files in base64 plus 1 MB) instead of the 300 MB of the other session routes. Every field is required: four booleans and two lists; any other field, a missing one or a wrong type is 400 and nothing is sent. `texts` are pasted texts (at most 20,000 characters each, not empty); `files` are `{format, bytesB64}` with `format` `docx`, `pptx` or `text` (UTF-8), strict base64, at most 20 MB each; at most 5 texts and files in all. `open_file` samples the file's saved version on disk (400 for a spreadsheet; 409 `changed_since` when the disk is not the version the session knows), leaving out paragraphs that stored agent or local runs wrote; `edits` adds the kept rewrites of the agent's text (400 when that is the only source and none are kept); `comments` adds the comments typed in this file (stamp taps left out); `improve` sends the saved guide as `current_guide` (400 when there is none). At least one of `open_file`, `edits` (with something kept), `texts` and `files` is needed (400 "Choose at least one sample of your writing."). Files are checked as packages (a macro-enabled one, a broken one or one past openZip's limits is 400) and sampled in a worker (`src/voice-sample-worker.js`, 60 s, `ONIONSKIN_VOICE_SAMPLE_TIMEOUT_MS`). The batch (`buildVoiceBatch`, `src/batch.js`) carries `instructions.voice_request` (code constants, plus `current_guide`), `style_note` when set, no `voice_guide`, no comments, an empty `file_name`, no anchors or user edits, the samples under `untrusted_document_evidence.voice_evidence`, no `how_to_apply`, and is trimmed until `poll` prints it in at most 28,000 characters (`ONIONSKIN_VOICE_BATCH_MAX_CHARS`). It goes to a waiting poller or waits like any batch, never to the local runner; a Send while it waits replaces it (as it replaces a waiting review) and adds a `voice` activity entry flagged `voice_request_replaced`. 409 `busy` while a batch waits or is delivered. While it is delivered, `agent-write` and `commit` are refused (409 `voice_only`). The agent answers with `reply` and `voice_draft`; `POST /cli/done` takes it in `results.voice_draft` (below). `{ok, session}`

At Send, `Sessions.send()` emits `voice` (`voiceJob` in `src/voice-learn.js`) and the server's listener stores it. Comment hits: the trait ids that `commentHits()` finds in the comments leaving draft in this Send, minus comments whose words are exactly a stamp's (built-in or own) and re-sent answered questions. Edit pairs: only when the file is DOCX, this Send wrote the person's bytes, the newest history update before it is an agent run that ended on exactly the bytes this Send started from, and the pre, post and sent versions are all still stored; then `src/voice-worker.js` runs on the three snapshot blobs in a worker thread (`ONIONSKIN_VOICE_TIMEOUT_MS`, default 60 s, then it is ended). Nothing at all while learning is off. A failure learns nothing and never fails the Send.

## Background settings (browser routes, per machine)

Not tied to a session and not editor-gated (a read-only tab may use them). Same cookie, launch token and, for writes, exact Origin and JSON content type as the other routes. The state is `<state>/settings.json` (0600), re-read on every request, so the CLI's `onionskin config background` shows after a page reload. `index.html` carries the choice as `data-bg` on `<html>` (the CSP forbids inline script).

| route | |
|---|---|
| `GET /api/settings` | `{background: {kind: 'preset'\|'custom', name, strength 0-100, blur}, customVersion, presets}`; default `paper`, strength 60, blur on; a missing or broken file, or `custom` without an image, reads as the default |
| `POST /api/settings {background}` | validates and stores; 400 for an unknown preset, a strength outside 0-100 or a non-boolean blur, 409 `custom` without a stored image. Returns the settings |
| `GET /api/background` | the stored picture (`image/png\|jpeg\|webp` from its magic bytes), 404 when none |
| `POST /api/background {bytesB64, background?}` | stores the picture as `backgrounds/custom.<ext>` (0600, one file, replaced), switches to `custom`. 415 unless PNG, JPEG or WebP by magic bytes, 413 above 15 MB. Any `path` or name in the body is ignored |
| `POST /api/background/remove` | deletes the picture; a `custom` choice falls back to the default preset |

## Deeper-check and quick-suggestion setup (browser routes, per machine)

The review panel's "Turn on deeper checks" button. Like the settings routes it is not tied to a session and not editor-gated (a read-only tab may use it), and it passes the same guards as every other route: exact Host, cookie, launch token, and for POST the exact Origin, `Sec-Fetch-Site: same-origin` and a JSON content type. It takes no parameters: the body is drained, checked as JSON and never read, and the command it runs is fixed (the same venv creation and pip install as `onionskin setup-checker`, with the base Python from `ONIONSKIN_BASE_PYTHON` or `python3`). Nothing from a page or a document reaches it. Code: `startSetupChecker`, `setupCheckerStatus` in `src/checker.js`. `GET|POST /api/setup-rewriter` is the same pattern for quick fixes (`startSetupRewriter`, `setupRewriterStatus` in `src/suggest.js`): POST turns on quick fixes with Apple's built-in model in the server (the same as `onionskin setup-rewriter`; nothing is downloaded) and answers at once; GET answers `{state: 'off'\|'working'\|'on'\|'failed', reason?, detail?}`, `on` when the helper is set up and intact, `reason` one of Apple's state codes (`macos_too_old`, `device_not_eligible`, `apple_intelligence_not_enabled`, `model_not_ready`, `quarantined`, `helper_missing`) or `failed`.

| route | |
|---|---|
| `POST /api/setup-checker {}` | starts the setup and answers at once with the status below (the server keeps serving while pip runs, about a minute). One job at a time: a second POST while one runs joins it. The job times out after 10 minutes (`ONIONSKIN_SETUP_TIMEOUT_MS`) |
| `GET /api/setup-checker` | `{state: 'off'\|'working'\|'on'\|'failed', reason?, detail?}`. `on` means the checker libraries import right now (whoever set them up). `failed` (the last job failed and the libraries still do not import) carries `reason` `no_python` \| `no_network` \| `failed` and `detail`, the technical text for a Details disclosure. A setup whose pip step exits 0 but whose libraries do not import is `failed`, never `on` |

After `on`, the next `done` uses the deeper check with no server restart (the checker is looked up on every run). `checks.deep.code` (see `ops.md`) tells the page whether the deeper check is "not set up" apart from "failed".
